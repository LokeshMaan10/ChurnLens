# Cleaning rules

_Generated by `python -m churnlens.data.clean` from the rule list in `src/churnlens/data/clean.py`; parameters come from `configs/cleaning.yaml`. Row counts are in `reports/results.md`._

## M1: members (set NULL)

- **Rule:** `age` = `bd` if 10 ≤ bd ≤ 90, else NULL; raw value kept in `bd_raw`, `age_invalid` flags it
- **Why:** Two thirds of `bd` values are 0 or negative; treating them as ages would be wrong.

## M2: members (set NULL)

- **Rule:** empty-string `gender` → NULL
- **Why:** Empty string means unknown; NULL makes that explicit.

## D1: all (parse)

- **Rule:** YYYYMMDD integers → DATE (`registration_date`, `transaction_date`, `membership_expire_date`, `date`)
- **Why:** Typed dates make cutoff filters and date arithmetic safe. Raw contracts already reject unparseable values, so no rows are lost.

## T1: transactions (select source)

- **Rule:** `transactions_source: v1_then_v2`: all v1 rows, plus v2 rows dated after 20170228 (the period v1 does not cover)
- **Why:** v2 rows inside v1's period restate old transactions with later expiry dates, which can encode snapshot B's label (see the effect table below). The build fails if any v2 row inside v1's period reaches the clean table under v1_then_v2.

## T2: transactions (drop)

- **Rule:** exact duplicate rows (within or across files) kept once; `source` = v1 / v2 / both
- **Why:** Identical rows are double-recorded; counting them twice inflates transaction counts.

## T3: transactions (drop)

- **Rule:** restatements (same transaction on every field except expiry, present in both files): keep the v2 version, set `restated`
- **Why:** `restatement_keep: v2`. Keeping both would double-count one transaction.

## T4: transactions (set NULL)

- **Rule:** `membership_expire_date` before 20040101 → NULL; `expire_implausible` flags it
- **Why:** Values like 1970-01-01 are placeholders, not real expiries.

## T5: transactions (keep + document)

- **Rule:** list price 0, plan days 0, paid > list price, and expiry before transaction date are kept unchanged
- **Why:** Plausibly real (free trials, promotions, plan changes, cancellations). Features in Phase 5 decide how to use them.

## L1: user_logs (cap)

- **Rule:** `total_secs` capped at 86,400; `secs_capped` flags it
- **Why:** A day has 86,400 seconds; larger values are logging errors, but the row's play counts are still informative.

## L2: user_logs (separate)

- **Rule:** `user_logs_v2` (March 2017) cleaned with the same rules but written to `scoring_only/` and exposed only as `user_logs_scoring`
- **Why:** It overlaps snapshot B's label period; it must never become a training input.

## Global uniqueness

Asserted in DuckDB after the build (batched pandera validation cannot see table-wide duplicates):

- `train`: unique on (msno)
- `train_v2`: unique on (msno)
- `members`: unique on (msno)
- `transactions`: unique on (msno, payment_method_id, payment_plan_days, plan_list_price, actual_amount_paid, is_auto_renew, transaction_date, membership_expire_date, is_cancel)
- `user_logs`: unique on (msno, date)
- `user_logs_scoring`: unique on (msno, date)
