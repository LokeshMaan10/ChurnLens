# Decisions log

Non-obvious choices, with the reason and the date decided. Newest last.

## Phase -1: data acquisition (2026-10-23)

1. **Download route: browser, not the Kaggle CLI.** No API token on this machine. Archives
   were downloaded through a signed-in browser session and moved into `data/raw/_downloads/`.
   `acquire.py` still uses the CLI automatically when `~/.kaggle/kaggle.json` exists.
2. **Hash sampling.** Keep a user iff `int(sha256(msno + str(seed)), 16) % 100 < pct`. The
   string concatenated is `msno` followed by the decimal seed (e.g. `"...=42"`). Deterministic
   per user, so the same users appear in every table and both snapshots.
3. **Streaming decompression with `py7zr`.** 7-Zip could not be installed (needs an admin
   prompt). A custom `py7zr` writer parses decompressed bytes in 64 MiB chunks, so no CSV is
   ever written to disk. The 30.5 GB `user_logs.csv` streamed in 26 minutes.
4. **`user_logs_v2` is exempt from the log window.** It covers March 2017, after
   `log_window_end` (2017-02-28); applying the window would drop every row. Only user sampling
   is applied, and the output lives under `scoring_only/`.
5. **Restartability is per table.** Each output is written to `*.tmp` and renamed after
   validation. An interrupted run redoes the interrupted table from the start (a stream
   cannot seek), and skips tables already recorded with matching checksums.
6. **Archives kept** (`keep_archives: true`), deviating from the spec's delete-by-default,
   because re-downloading without a token takes about 1.5 hours by browser. Confirmed by the user.
7. **Raw layer keeps source encodings.** Dates stay `YYYYMMDD` integers and no values are
   cleaned; parsing and cleaning happen in Phase 1 with documented rules.

## Phase 0: setup and audit (2026-10-23)

8. **Python 3.11 venv** at `.venv` (system default is 3.13; the spec requires 3.11).
9. **`results.md` is written in sections.** Each phase replaces only its own
   `<!-- BEGIN:key -->` block, so phases can be re-run independently.
10. **Data dictionary = hand-written meanings + generated stats.** Meanings live in
    `docs/columns.yaml`; `data_dictionary.md` is regenerated by the audit.
11. **Audit thresholds** (plausible age 10–90, 86,400 s/day, earliest plausible date
    2004-01-01) live in `configs/audit.yaml`. The audit flags; it does not clean.

## Phase 1: data layer (2026-10-23)

12. **Transactions: `v1_then_v2` (leak fix, user decision 2026-10-23).** A first build used
    v1 + v2 in full (`combined`). That leaked: v2 rows dated before 2017-03-01 that are absent
    from v1 all expire on or after 2017-04-01, changing the latest pre-cutoff expiry for 9,355
    snapshot B users (9.6%). The fix keeps all history from v1 and takes from v2 only rows dated
    after `v1_coverage_end` (2017-02-28). The effect drops to 0 users, and the build fails if
    any v2 row inside v1's period reaches the clean table. `combined` and `v1_only` remain
    selectable in `configs/cleaning.yaml`; every row keeps a `source` column.
13. **Restatements keep v2** (`restatement_keep`). This only matters under `combined`; under
    `v1_then_v2`, v1 and v2 date ranges don't overlap, so no restatements can occur.
14. **Exact duplicate rows are collapsed**, on the view that identical rows (same expiry too)
    are double-recorded rather than two real purchases.
15. **Implausible values become NULL, not dropped** (age outside 10–90, expiry before 2004),
    with the raw value or a flag kept. Long log days are capped at 86,400 s, not dropped,
    because the play counts on those rows are still informative.
16. **Logs v1 and v2 are not merged.** The spec asked to dedupe logs across files, but
    `user_logs_v2` is scoring-only and shares no (msno, date) keys with `user_logs`. It is
    cleaned separately and exposed only as the `user_logs_scoring` view.
17. **Clean tables are materialised as Parquet; the DuckDB file holds only views.** The
    database stores absolute paths, so it is rebuilt by `make clean-data` on each machine.
18. **Global uniqueness is asserted in DuckDB**, because pandera validates in 1M-row batches
    and cannot see table-wide duplicates.

## Phase 2: snapshots (2026-10-23)

19. **Snapshot directories are the only feature inputs.** Each holds labels plus
    transactions, logs and members restricted to label users and to timestamps strictly
    before the cutoff. Features (Phase 5) must read from them, never from the clean layer.
20. **Members registered on/after the cutoff** keep their row, but `registration_date` is
    set NULL and `registered_after_cutoff` flags it (A: 91 users, B: 120). Other member
    attributes (city, age, channel) come from a single undated extract, so whether they
    changed after the cutoff cannot be checked; this is a documented residual risk.
21. **Labels are used as provided.** Rebuilding KKBox's rule from transactions agrees 97.75%
    for snapshot A. For snapshot B the 30-day window runs past the end of the data
    (2017-03-31) for 99.9% of users, so it cannot be fully checked; 3,747 of 8,515 B churners
    with a March expiry show a renewal-like March transaction. The labels are not altered.
22. **Label verification may read post-cutoff transactions**, because it checks the target,
    not features; its outputs are written to `label_verification.json` and never read by
    feature code.
23. **Leakage tests run on the built files** (`tests/test_leakage.py`) and are skipped, not
    passed, when the snapshots have not been built. A deliberate one-day cutoff shift was
    confirmed to make them fail.

## Phase 3: EDA (2026-10-23)

24. **EDA uses snapshot A only.** Snapshot B is the out-of-time test set; looking at its
    labels during exploration would bias later modelling choices. (The calendar check reads
    B's pre-cutoff logs without labels, to describe input drift.)
25. **Deterministic tie-breaking everywhere a "first"/"last" row is picked.** Same-day
    transactions tie on date; ordering by every column makes results identical run to run.
    A real bug found this way: two window functions broke ties differently and split
    subscription spells. Both now share one row number. Three consecutive runs produce
    byte-identical tables.
26. **Exact sums for listening seconds** (`DECIMAL`), because parallel float sums vary in
    the last digits between runs. CSV floats are written to 10 significant digits.
27. **Subscription spells for survival analysis** are rebuilt from all sampled users'
    pre-cutoff transactions (30-day gap = churn). Spells first seen before 2015-03-01 are
    dropped (left truncation); cancellations do not shorten spells (limitation, revisit in
    Phase 8).
28. **Calendar effect, not a tested cause:** all-user activity in the 7 days before snapshot
    A's cutoff is 6% lower and coincides with the 2017 Lunar New Year holiday; no such dip
    before snapshot B. Expect short-window listening features to drift between snapshots.

## Phase 4: RFM and segmentation (2026-10-23)

29. **Tie-aware quantile scores instead of plain quintiles.** Recency piles up at 1 day
    (half of recent listeners) and monetary at a few plan totals (894 / 594 NTD), so quintile
    edges collapse. Score = ceil(5 x share of reference users at or below the value), recency
    inverted: ties always share a score and the best value always scores 5, but some levels
    go unused (recency never scores 4). The score distribution is reported.
30. **Scores and K-Means are fitted on snapshot A and applied unchanged to B**, so the test
    snapshot is never scored against its own distribution. Churn by segment is reported for
    A only.
31. **Segment rules live in `configs/rfm.yaml`** as DuckDB SQL predicates evaluated in
    order (first match wins) and must end with a catch-all; a test checks every score
    combination gets exactly one segment.
32. **Finding: engagement-based RFM separates churn weakly** (Cramér's V 0.066, vs 0.38 for
    auto-renew in Phase 3). Users with no listening in 90 days churn at 6.5%, close to the
    6.4% base rate.
33. **K-Means clusters only users who paid and listened (user decision).** Clustering
    everyone mostly isolated two piles (paid 0 NTD, at -6.4 SD after scaling; 0 listening
    days) that two if/else rules reproduce for 87.9% of users; a "paid 0" flag matched its
    churn gain (V 0.295 vs 0.296). Now `kmeans.population` = `monetary > 0 AND
    frequency_days > 0` (79.9% of A); everyone else gets an explicit rule-based "not
    clustered" label. Cluster numbers follow size (1 = largest) for run-to-run stability.
    Result on A: k=3 (silhouette 0.452); gain within the population +0.077 in Cramér's V,
    so K-Means is kept. Cluster 3 (median 198 NTD paid in 180 days) churns at 15.2%.

## Phase 5: feature engineering (2026-10-23)

34. **Features are built only from snapshot directories**, and the builder re-applies the
    cutoff to every input. A test writes label-window rows into a snapshot and checks the
    features do not change; another checks feature SQL never references the clean layer or
    scoring-only data.
35. **One registry documents every feature** (`src/churnlens/features/registry.py`):
    definition, rationale, leakage risk, and whether the model may use it. The build fails
    if its output columns differ from the registry; the data dictionary is generated from it.
36. **Gender, age and city are built but excluded from the model** (`configs/features.yaml`,
    `demographics.use_in_model: false`). Reasons: gender and age are protected
    characteristics, and retention offers targeted on them risk unfair treatment; city can
    act as a proxy for them. Age is missing or invalid for 61% of snapshot A users and
    gender for 49% (Phase 3), so much of their apparent signal is missingness. Their
    single-feature association is modest (age AUC 0.397). They stay in the feature table
    for the Phase 6 fairness audit, which reports error rates by these groups either way.
    Registration channel stays in the model: it is a business attribute (acquisition
    channel), not a personal characteristic.
37. **Post-cutoff registrations look like missing member data.** A user who registered on
    or after the cutoff gets every member attribute NULL and `member_info_missing = 1`, the
    same as a user with no members row; otherwise NULL tenure next to a known city would
    reveal the post-cutoff registration.
38. **Exact arithmetic for listening features.** Seconds stay DECIMAL through every sum;
    slope and CV are computed from exact sums. A first version used float sums and 66
    users' `minutes_per_active_day_30d` differed in the 8th decimal between runs.
39. **Leakage alarm** in the report: any single feature with strength above 0.8 is flagged.
    None was; the strongest is `last_is_auto_renew` at 0.488 (AUC 0.256).

## Phase 6: modeling (2026-10-23)

40. **Every modelling choice is made on snapshot A; B is scored once at the end.**
    Hyperparameters (randomized search, 5-fold stratified CV, PR-AUC), the calibration
    method, the model family, and the contact threshold all use A only (out-of-fold
    predictions where a held-out view is needed).
41. **Class weights, no SMOTE.** With 6,382 churners in A there are enough minority
    examples for the models; SMOTE would add synthetic rows that distort predicted
    probabilities, and this project uses calibrated probabilities to value risk
    (P x CLTV in Phase 9). Class weights also inflate probabilities, which calibration
    then corrects; the raw-vs-calibrated comparison is reported.
42. **Calibration is fitted on out-of-fold predictions.** The method (isotonic vs Platt)
    is chosen by cross-validated Brier score on A's OOF probabilities, then fitted on all
    of them and applied to B.
43. **Costs are placeholders** (`configs/costs.yaml`: offer 30 NTD, churn loss 600 NTD,
    save rate 25%). The threshold minimises realized cost on A's calibrated OOF
    probabilities. Replace them with real figures (Phase 8 CLTV, Phase 10 experiments)
    and re-run.
44. **LightGBM stands in for "LightGBM/XGBoost"**: one gradient-boosting family keeps
    run time reasonable; XGBoost can be added as another `models:` entry.
45. **MLflow uses a local SQLite store** (`mlruns/mlflow.db`): MLflow 3 rejects the plain
    folder store. A smoke run (1 search iteration per family) is logged under the
    separate experiment `churnlens-smoke`.
46. **Rank with the raw score; use calibrated probabilities for values (user decision).**
    The first full run chose isotonic calibration (Brier 0.0397, tied with Platt to four
    decimals on A). Isotonic is a step function, so it created ties that blurred the
    ranking: LightGBM's B PR-AUC was 0.574 on the raw score vs 0.563 on the isotonic
    output. Now PR-AUC, ROC-AUC, top-K, lift, gains and curves use the raw score; log loss,
    Brier, calibration tables, mean prediction, the threshold and the fairness rates use
    the calibrated probability; and calibration methods within 0.0001 Brier of the best
    count as tied, with ties going to sigmoid (strictly monotone).
47. **Known open issue: probabilities run low on B.** The first run predicted a mean of
    6.7% on B against 9.1% actual (A's base rate is 6.4%). Calibration fitted on A cannot
    anticipate a base-rate shift; Phase 14 (drift monitoring and recalibration) owns this.

## Phase 7: explainability (2026-10-24)

48. **Exact TreeSHAP on the raw score.** SHAP explains LightGBM's log-odds output, not the
    calibrated probability; sigmoid calibration is monotone, so every driver's direction
    carries over. One-hot columns are summed back to their feature (SHAP is additive), and
    base + sum = raw score is asserted for all 97,237 snapshot B users (max error 9e-12 in
    the check). The recomputed probabilities match Phase 6 to 5e-11.
49. **Drivers are reported per correlation cluster** (|Spearman rho| > 0.8, average
    linkage), so near-duplicates such as minutes_7d / 14d / 30d count once. Each customer
    gets up to 5 risk-raising clusters, described by that customer's strongest member.
    Reason codes state values neutrally from `configs/reason_codes.yaml` and always end with
    "associated with higher/lower predicted churn risk".

## Phase 8: survival and CLTV (2026-10-24)

50. **BG/NBD + Gamma-Gamma not used (spec conflict).** BG/NBD models non-contractual
    purchasing where customer death is unobserved; KKBox is contractual (expiry dates and
    churn are observed) and prices are fixed plan amounts, which breaks Gamma-Gamma's spend
    model. The second CLTV method is survival-based (Cox conditional survival) instead.
51. **CLTV = expected discounted margin over 12 months if the customer renews now**, so
    that Phase 9's P(churn) x CLTV is the value lost if they churn at this renewal. Margin
    (70%) and discount rate (10%/yr) are placeholders. Free or zero-price plans are valued at
    their list price, else the median paid price (assumes conversion).
52. **Survival CLTV chosen for Phase 9 by backtest.** On snapshot A renewers with 30-day
    plans, both methods predicted the next 59 days' revenue within 5-6% in total; survival
    had the lower per-user MAE (27.8 vs 29.0 NTD). Only 2 of 12 months can be backtested.
    The Cox proportional-hazards assumption is violated for 8 of 11 covariates
    (Schoenfeld test), so hazard ratios are time-averaged.

## Phase 9: prioritization (2026-10-24)

53. **Optimizer ranks by benefit - lambda x cost, searching lambda.** A first version ranked
    by benefit per NTD, the classic knapsack heuristic, but here the contact cap binds before
    the budget: it filled 4,000 slots with 5-NTD reminders, spent 20k of 150k, and lost to a
    plain "highest risk first" list. Searching lambda (0 to 1000) reaches 99.4% of the LP
    upper bound. Tests cover both the cap-binding and budget-binding cases.
54. **Action costs and save rates are placeholders** (`configs/prioritize.yaml`); only the
    labels-based columns (churn rate of the contacted list) are real outcomes. Observation:
    no high-risk user's top driver is listening-related, so the listening rule never fires.

## Phase 10: experiments (2026-10-24)

55. **Simulated outcomes are labelled SIMULATED everywhere.** Outcomes come from calibrated
    P(churn) with fake effects (10% / 30% relative reduction). The planned design (80/20
    randomized holdout on high-risk users) and the power table are real calculations. The
    SRM demo uses a 15% control loss: a 5% loss was not detectable at this sample size
    (p = 0.075). The T-learner ranks uplift in the right direction (correlation 0.31 with
    the fake truth) but exaggerates magnitudes, given a ~780-user control training arm.

## Phases 11-16: tools, agents, monitoring, app, hardening (2026-10-24)

56. **One tool layer for agents, MCP and the app** (`tools/core.py`). The MCP server uses the
    official SDK, which is 2.x here (`MCPServer`, formerly `FastMCP`); every tool is annotated
    read-only and expected refusals return an MCP error that states the reason.
57. **Read-only SQL is enforced, not requested.** One statement, type SELECT only, no
    file-reading table functions, row cap, timeout, in-memory connection over Parquet views.
    Tested with DROP/DELETE/UPDATE/INSERT/CREATE/COPY/ATTACH/SET/PRAGMA/read_csv and
    multi-statement injection.
58. **Agents default to an offline mode (user decision: no paid API).** Deterministic intent
    parsing and templates call the same tools. The Claude mode (manual tool loop, adaptive
    thinking, model id from `CHURNLENS_MODEL`) is implemented but was not run.
59. **Grounding is checked mechanically.** Every number in an answer must appear in a tool
    output or the question (at the displayed precision, or as a percentage of a share). The
    planner's holdout split moved into a `design_ab_test` tool after the check flagged numbers
    the agent had computed itself.
60. **Golden set as regression set.** First run: 91.1% numeric/SQL accuracy, 84.3% grounded,
    73.3% safety. Causes: "action" matched inside "transactions"; "12-month" and a timestamp
    hour were constants, not tool outputs; the disclaimer itself said "not causes", tripping the
    causal-wording check. All fixed; final run 100% on all, but the set no longer measures
    generalisation (stated in the report).
61. **Monitoring separates structural from behavioural drift.** The one feature in major drift,
    `days_since_first_transaction` (PSI 0.687), rose by exactly 28 days for all 88,027 users in
    both snapshots (the cutoff gap), and 31% of A users' first transaction is in January 2015,
    when the data starts. It is classified as a structural (clock) shift. Recommendation:
    cap or re-anchor it and retrain (not done here).
62. **Retraining fires on calibration, not drift.** Prediction PSI is 0.019 (stable), but mean
    predicted churn on B is 2.4 points below observed (policy threshold 2 points).
63. **Live scoring uses a separate snapshot C** (April 2017 expirations, cutoff 2017-04-01) —
    the only consumer of the scoring-only March logs; written under `scoring/`, never trained
    on. CLTV there is the formula method because the Cox model object is not persisted.
64. **Docs are generated from outputs** (`churnlens.docsgen`): README results and
    `reports/interview_walkthrough.md` contain no hand-typed figures.
65. **Docker and CI written, Docker not built** (Docker Desktop was not running). CI runs ruff
    and pytest; data-dependent tests skip when outputs are absent.
